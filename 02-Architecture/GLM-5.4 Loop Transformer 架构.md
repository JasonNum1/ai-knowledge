# GLM-5.4 Loop Transformer 架构

**核心结论**：Loop Transformer（循环 Transformer）让一组**共享权重**的层循环执行多轮——同一个函数反复迭代逼近更优解，以此换取"参数量不变但网络更深"的效果。对后端开发者而言，它不是把查找表造得更大（堆参数），而是让同一段代码多跑几遍、每遍在上一遍结果上继续精化。GLM-5.4 是智谱首代采用该架构的旗舰模型，对 GLM-5 基座中的 28 层做两轮循环，官方称其智能水平达到 2-3T 级模型，同时把循环带来的显存与检索开销压到最低。

## 是什么

- 标准 Transformer 的每一层在一次前向计算中只执行一次；Loop Transformer 让一组共享权重的层**循环执行多轮**，每一轮在上一轮隐状态（Hidden State）的基础上继续推演、细化结果，等效得到一个更深的网络。
- GLM-5.4 对 GLM-5 基座中的 28 层做两轮循环（共享权重 ×2）。
- 想法源自 2018 年的 Universal Transformer（权重共享的深度结构）。但纯权重共享在同等预训练计算量下效果弱于非共享权重模型，因此 GLM-5.4 **不是从头预训练**，而是把已完成预训练的基座通过继续训练改造为 Loop Transformer——以较小算力开销换取智能上限提升。

## 为什么需要

- 基础洞察：**记忆型任务受益于更多参数，推理型任务受益于更多有效计算**。
- 大型软件工程、网络安全、3D 建模与物理控制本质上是极长链路的推理任务：模型必须沿多步因果链持续推演并保持全局逻辑自洽，这类能力无法靠堆参数、死记硬背获得。
- Loop 属于"扩展计算深度"路线：与扩展模型大小并进，而非二选一。

## 怎么工作：三项 750B 规模工程改动

直接把中间层改成多轮循环会遇到三个工程问题，GLM-5.4 逐项解决：

### 1. 门控渐进更新

- **问题**：若每轮输出直接覆盖隐状态，激活范数（Activation Norm）会随循环轮数过度膨胀，后续层收到的表示偏离原模型熟悉的尺度与分布。
- **做法**：为每一轮设置独立的逐 token 门控（Gating），按比例将该轮的候选变化写回残差流（Residual Stream）。
- **训练后呈现的分工**：第一轮侧重建立全局上下文状态，对多数位置以较小门值温和写回以稳住尺度；第二轮复用该状态完成精炼，放开门控、充分写回结果。
- 门控还会按 token 预测难度**动态调节步长**：越难预测的位置，首轮写入会适度加大，让复杂预测更充分受益于多轮迭代。

### 2. KV Cache（键值缓存）全局共享 + 滑动窗口（Sliding Window）独立

- **问题**：朴素做法为每轮循环保留一整份 KV Cache，显存随循环轮数成倍增长。
- **做法**：跨轮共享 KV 的基础上，用滑动窗口补充新一轮的局部信息——第二轮复用第一轮选出的稀疏 KV，同时保留滑动窗口内由第二轮生成的 KV。两路 KV 可以覆盖同一位置，让模型既能读取第一轮的上下文表示，也能利用第二轮更新后的局部表示。
- **效果**：多一轮循环的额外代价只是**一个窗口的 KV**，而非一整份全上下文 cache；在 1M 长上下文下部署成本增幅保持可控。

### 3. 复用稀疏注意力索引

- **问题**：GLM-5.4 的基座采用稀疏注意力（Sparse Attention），第二轮循环若重新计算索引，会增加索引器开销。
- **做法**：第二轮循环直接复用第一轮索引器生成的索引，实验显示与每轮重算效果几乎相当。

## 规模验证（Scaling Correctness）

架构创新必须在规模放大后依然成立。验证路径：1B → 4B → 30B → 750B 基座逐级验证；在与 750B 基座架构完全相同的 30B 模型上做同参数量对比（经 200K 长文本 SFT 后、开启 thinking 评测），整体训练计算量仅增加约 10%，Loop 版本相对基线有明显提升。

两个关键发现：

- **推理链越长，Loop 的帮助越大**：提升最大的是数学推理、长上下文和代码——正是泛 Coding 最依赖的能力。
- **Loop 用更少的 token 思考**：GPQA、MMLU-Pro 等基准上平均输出长度下降 10%–14%，缩减主要来自思维链（Chain of Thought）。一部分推理从 token 流转移到了循环带来的额外深度中。

## 模型定位与能力（泛 Coding）

- **泛 Coding**：代码已成为模型能力外推的基础能力。官方进行了 200 个真实场景的编程实战评测，GLM-5.4 在视觉 Coding、视觉复刻和长程任务（Long Horizon Task）中表现突出。
- **Coding 外推场景**：
  - Video：画面用前端代码实时绘制（0 图像素材），音乐自主计划并调用第三方生成模型完成多轮 Prompt 修改
  - 3D：纯数学几何 + 自定义 GLSL 着色器从零生成 3D 微距互动体验
  - Engineering：FreeCAD 工程化建模六轴机械臂 + Blender 动作设计与可视化
- **推理速度（官方数据）**：非高峰时段最高 200 token/s，高峰时段 70–80 token/s。实现依赖结构与推理 Infra 协同：KV Cache 按距离拆分、稀疏注意力索引复用、核心算子融合减少中间结果显存读写。
- **已知现象**："雷霆大思考"——模型容易进入长时间思考模式，但长思考可持续提升效果（思考中不断反思、自我修正），官方视其为长程任务一直想要的能力。

## 与后端概念的对应

| Loop Transformer 概念 | 后端类比 |
|---|---|
| 共享权重层循环多轮 | 同一段代码多轮迭代逼近近似解（迭代法），而非建更大的查找表 |
| 门控写回残差流 | 乐观更新按比例合入主分支，难度高的位置合入更大步长 |
| KV Cache 全局共享 + 滑窗独立 | 共享只读缓存 + 本地写缓冲，只多付出缓冲区大小的代价 |
| 复用稀疏注意力索引 | 缓存查询计划/索引，避免每轮重新建索引 |

## 遗留问题

- 自适应计算（Adaptive Computation）：如何让不同难度的 token 获得不同的循环计算量。
- 循环轮数与模型规模继续增大时，Loop 收益的变化规律尚未回答。
